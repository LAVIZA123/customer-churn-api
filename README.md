# Customer Churn Machine Learning API & Batch Scoring Deployment

## 1. Project Overview
This repository implements an end-to-end Machine Learning deployment solution for customer churn prediction. Built with **Flask** and **scikit-learn**, it provides real-time API inference and automated batch scoring capabilities for customer datasets.

The system preprocesses raw customer attributes using a fitted `ColumnTransformer` (imputing numerical features and one-hot encoding categorical features) and feeds transformed features into a trained classification model to compute churn probabilities and predictions ("Yes" / "No").

## 3. Installation Instructions

1. **Clone the repository**:
   ```bash
   git clone <repository_url>
   cd customer-churn-api
   ```

2. **Set up a virtual environment (optional but recommended)**:
   ```bash
   python -m venv venv
   # On Windows:
   venv\Scripts\activate
   # On Linux/macOS:
   source venv/bin/activate
   ```

3. **Install dependencies**:
   ```bash
   pip install -r requirements.txt
   ```

4. **Train Model & Preprocessor (if re-generating artifacts)**:
   ```bash
   python train.py
   ```

## 5. How to Test `/predict` Endpoint

### Health Check Endpoint (`GET /health`)
Verify API status:
```bash
curl http://localhost:8000/health
```
**Expected Response:**
```json
{
  "status": "ok"
}
```

### Inference Endpoint (`POST /predict`)
Send a sample customer payload:
```bash
curl -X POST http://localhost:8000/predict \
  -H "Content-Type: application/json" \
  -d @test_data/sample_input.json
```

**Expected Response Format:**
```json
{
  "churn_probability": 0.83,
  "churn_prediction": "Yes"
}
```

## 6. How to Run `batch.py`

Run the batch scoring pipeline against a customer CSV file:

```bash
python batch.py --input test_data/all_customers.csv
```

### Workflow Highlights:
- Reads input customer records line-by-line.
- Strips the target column `Churn` before dispatching API requests.
- Queries `http://localhost:8000/predict`.
- Appends `churn_probability` and `churn_prediction` columns.
- Saves results to `scored_customers.csv`.

---

## 7. Expected Output Files
- `scored_customers.csv`: Contains input customer records augmented with model predictions (`churn_probability` and `churn_prediction`).
- `logs/batch_log.txt`: Contains summary metrics and execution logs.
- `app/model.pkl`: Serialized trained machine learning model.
- `app/transformer.pkl`: Serialized feature preprocessing pipeline.

---

## 8. Logging Information
Batch execution logs are written to `logs/batch_log.txt` using Python's standard `logging` module. 

Log entries include:
- Total number of processed API requests
- Total successful predictions
- Total failed predictions
- Average churn probability across processed customers
- Error tracebacks for non-200 API status responses or network failures

## 9. Maintenance Plan

### Retraining
The churn prediction model and feature preprocessor will undergo scheduled monthly retraining using newly accumulated customer churn data. Retraining can also be triggered asynchronously whenever model prediction accuracy or ROC-AUC drops below pre-established baseline performance thresholds (e.g., ROC-AUC < 0.78). Automated retraining scripts validate that newly trained models outperform existing production models on holdout validation datasets before updating `app/model.pkl` and `app/transformer.pkl` artifacts.

### Drift Detection
Data drift and concept drift will be continuously monitored by comparing incoming feature distributions (such as `tenure`, `MonthlyCharges`, and `TotalCharges`) against baseline distributions from `gold_churn_data.csv` using Kolmogorov-Smirnov (KS) statistical tests for numerical variables and Chi-Square tests for categorical attributes. Prediction output drift is tracked by monitoring rolling 7-day average churn probabilities in `logs/batch_log.txt`. Significant distribution shifts trigger automated alerts for data engineering and MLOps teams.

### Versioning
All model artifacts (`model.pkl`) and preprocessing pipelines (`transformer.pkl`) are versioned alongside codebase releases using Semantic Versioning (e.g., `v1.2.0`). Production model artifacts are stored in an artifact registry with metadata tracking training datasets, hyperparameter configurations, evaluation metrics, and Git commit hashes. Pipeline and model versions are bound together to ensure full compatibility during inference.
